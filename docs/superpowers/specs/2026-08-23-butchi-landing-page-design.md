# Butchi Landing Page + Real Screenshot CI Design

## Goal
Create a first-class Butchi product page at `https://dhhieu113pro.github.io/butchi/` that uses real, deterministic screenshots of the Windows app generated by CI rather than repository illustration SVGs.

The page should explain the product in one glance: select text anywhere in Windows, Butchi appears beside it, Translate or Rewrite runs through a local GGUF model, and user text stays local.

## Repositories and ownership

Owns product truth, visual assets, deterministic screenshot state, screenshot CI, and the static Butchi product page source.

Expected production changes:
- Create: `.github/workflows/screenshots.yml`
- Create: `scripts/capture-ui.ps1`
- Create: `docs/index.html`
- Create: `docs/privacy.html` or reuse/link the existing `PRIVACY.md` through GitHub if a dedicated web privacy page is unnecessary during implementation review.

- Modify: `src/settings.ts` only if deterministic Settings screenshot state cannot be derived from existing defaults/config without side effects.
- Modify: `src-tauri/src/lib.rs` to support screenshot mode that opens the correct real Tauri window(s) and disables background selection/keyboard monitors during capture.
- Modify: `README.md` to point screenshots/product website to the real PNG captures after the workflow is proven.

No existing production route/component/file is deleted.

### `dhhieu113pro/dhhieu113pro.github.io`

## Screenshot architecture

### Why a dedicated screenshot mode
The existing repository screenshots are SVG illustrations and the README explicitly says Store screenshots should be real captures. The public landing page should likewise use real app UI.

Normal Butchi startup is unsuitable for deterministic CI screenshots because it starts tray/selection/keyboard behavior, may open first-run model setup based on local state, and the popover normally depends on a real user selection plus model execution.

Screenshot mode therefore must be explicit and inert outside CI/dev capture.

### Activation
Use an environment variable, for example:

`BUTCHI_SCREENSHOT_MODE=settings-light|settings-dark|popover-light|popover-dark`

Normal users never set this variable, so production behavior remains unchanged.

### Native startup behavior in screenshot mode
In `src-tauri/src/lib.rs`:
- detect `BUTCHI_SCREENSHOT_MODE` during setup;
- do not start the selection monitor or keyboard monitor;
- do not force first-run model download/setup based on model availability;
- open only the window needed for the requested capture;
- position/size the target window deterministically;
- for Settings, open the existing real `settings.html` Tauri window;
- for Popover, show the existing real `popover` Tauri window;
- keep tray creation optional/off during screenshot mode so CI does not depend on notification-area behavior.

### Frontend deterministic state
Screenshot mode must never call a model, require a model download, or fabricate a fake app shell.

The existing real page DOM/CSS is used. Only its data state is seeded.

#### Popover screenshot data
Use a deterministic example such as:
- source: `Could you send the updated report by Friday?`
- translation: `Bạn có thể gửi báo cáo đã cập nhật trước thứ Sáu không?`
- rewrite: `Could you please send the updated report by Friday?`

The strings are labelled/demo content, not represented as a real model benchmark.

In screenshot mode the frontend renders the same selection/result-card functions/classes as normal execution but skips invocation of `process_text_stream`.

Capture should show a useful completed-state composition with Translate and Rewrite results and real Copy/Replace affordances.

#### Settings screenshot data
The real Settings page loads its current controls. Screenshot mode may provide deterministic configuration/model-status responses through a narrow native screenshot fixture layer if required, or use seeded config in the runner's app-data directory before launching.

Preferred approach: seed the existing persisted config/app-data before launch so Settings continues to exercise the normal `get_config` / `get_model_status` interfaces. Avoid duplicating a second Settings renderer.

Screenshot should show:
- the redesigned navigation;
- Model page or General page in a meaningful ready/configured state;
- no download in progress;
- no secret/local machine paths visible in the final capture.

### Light/dark modes
The runner sets the page/app theme deterministically for each capture. Do not rely on whatever Windows runner theme happens to be active.

Produce exactly four canonical website captures:
- `docs/shots/popover-light.png`
- `docs/shots/popover-dark.png`
- `docs/shots/settings-light.png`
- `docs/shots/settings-dark.png`

Additional temporary screenshots may remain CI artifacts but should not become public docs assets unless the page actually needs them.

## Windows capture workflow

Create `.github/workflows/screenshots.yml` with `workflow_dispatch` and optional triggers on changes to UI files.

Use `windows-latest` for canonical website screenshots.

High-level flow:
1. checkout Butchi;
2. install Rust/Node/CMake dependencies already proven by CI;
3. build the actual Tauri application with the same frontend and local-LLM feature configuration used by the app;
4. launch the built executable four times with the corresponding screenshot mode;
5. wait until the target window exists and its UI is stable;
6. capture the target window rectangle to PNG via `scripts/capture-ui.ps1` using Windows APIs/.NET screen capture rather than photographing the entire runner desktop;
7. validate each PNG exists and has non-trivial dimensions/file size;
8. upload all four as an Actions artifact named `butchi-ui-screenshots`;
9. on trusted `main`/manual runs with write permission, commit/update the four canonical files under `docs/shots/` only when bytes changed.

The capture script accepts a window title/selector and output path, resolves the native HWND, reads its actual bounds, captures that rectangle, and exits non-zero when the target window is missing or dimensions are implausible.

Do not use OCR to validate the screenshots.

## Error/fallback behavior

### Screenshot CI failure
If capture cannot find a target window or a PNG fails validation, the screenshot workflow fails and does not overwrite the last known-good `docs/shots/*` images.

### Pages build
Pages always deploys the committed, last-known-good Butchi screenshots. It does not depend on downloading an artifact from the latest screenshot run at deployment time.

This deliberately decouples public-site reliability from screenshot-run timing.

### Missing Store listing
Display `Microsoft Store — Coming soon`; never link to an unconfirmed Store URL.
